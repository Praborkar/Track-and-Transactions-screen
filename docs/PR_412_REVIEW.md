# Review of PR #412, "Track: load transactions from the new API"

**Do not merge.** Nine of the ten comments break a rule the screen has to keep. The first three can crash the screen or empty it on this very server. The earlier approval does not change that, and I would ask the approving reviewer to look again at comments 1 to 3.

Line numbers refer to `review/useTransactions.ts` (hook) and `review/TrackScreen.tsx` (screen). The last column says how my own app avoids the same problem and where the test is.

| # | Verdict | Where | What breaks, and the row or number that shows it | My app |
|---|---|---|---|---|
| 1 | Block | hook :30-37, screen :31 | A failed request wipes the list. `res.ok` is never checked, so on the server's 500 (the 6th list call) `body.items` is undefined, the spread on line 32 throws, and the catch on lines 34-37 sets `transactions` to `[]` and shows only "Something went wrong". The user loses the ~245 rows already on screen. A 429 (11th call) does the same. | Errors never touch stored rows. A banner says what failed and offers Retry. `sync.test.ts`, "a failure never costs what was visible" (500, 429, dropped connection). |
| 2 | Block | hook :57, :11 | Only the new record shape is read. 2,281 of the 4,675 rows (everything before 1 April 2026) have `txn_time` and a string `amount`, and no `occurred_at`, so `t.occurred_at.slice(0, 7)` throws a TypeError as soon as scrolling reaches them, around row 2,394. `amount_minor` is also undefined on those rows, so the row would print "NaN". | `normalize()` reads both shapes and rejects unknown ones without throwing. `domain.test.ts`, "two record shapes, one list". |
| 3 | Block | hook :32 | Each page repeats the previous page's last row (the cursor is `offset + limit - 1`), and rows are appended without checking ids. With `limit=100` the app receives 4,722 rows for 4,675 distinct ids, so 47 transactions show twice and count twice. | Merge by id. `domain.test.ts`, "every transaction appears once". |
| 4 | Block | hook :63-67 | `monthTotal` adds every debit. Own-account transfers count as spending. The ₹25,000 self transfer from HDFC to ICICI on 3 Oct 2026 would be added to October: ₹1,34,784.98 shown instead of ₹1,09,784.98. Card bill payments (12 of them) have the same problem. There is also no "earned" figure anywhere, and the screen has to show it. All 13 months come out wrong. | Rows with `counterparty.type = OWN_ACCOUNT` or `linked_account` are left out. Spent and earned are both shown. `domain.test.ts`, "own-account transfers…". |
| 5 | Block | screen :7-8, :40-41; hook :66 | Money is summed as floats (`amount_minor / 100`), and floats are not guaranteed to add up to the paisa. Formatting uses `en-US`, so ₹12,34,567.89 (the April bonus) prints as ₹1,234,567.89, which Indian users read wrongly. The month header uses `toFixed(2)` with no grouping at all: ₹109784.98. | Integer paise everywhere, and `formatInr` with 2-digit grouping. `domain.test.ts`, "money is exact" and "reads like our users read it". |
| 6 | Block | screen :7-8, :16 | `currency` is ignored. The $10.00 Notion charge (`amount_minor` 1000) shows as ₹10.00 and is added to rupee totals. The API supplies `fx.inr_minor` (86,661 paise, ₹866.61). 15 rows are affected. | Totals use the rupee value. The detail screen shows both. A row with no rate is left out and labelled "Not converted". `domain.test.ts`, "foreign currency". |
| 7 | Block | hook :49 | Pull to refresh runs `load(true)`, which replaces the whole list with the first 50 rows, so every older month disappears. The changes feed is never used, so the 7 deleted transactions stay visible, the 43 edited or new records never arrive, and the 25 pending rows stay pending (the feed changes 21 of their statuses). | Refresh calls the changes feed with the stored token and merges. It falls back to a full sync only on a 410. `sync.test.ts`, "the server rejects our token (410)", and `checkpoint.test.ts`. |
| 8 | Block | hook :26-47 | `onEndReached` can fire while a load is running, and `load` reads `transactions` and `cursor` from an old render. Two loads run at once with the same old state, so the second result overwrites the first. Rows are dropped or added twice and the cursor can go backwards. | One sync at a time. `requestSync` returns the running promise, and a stale run cannot write. `sync.test.ts`, "two syncs at once". |
| 9 | Block | hook :57 | Months come from `occurred_at.slice(0, 7)`, which is UTC. 43 rows land in the wrong month for a user in India, a September 2025 appears with 2 rows that belong to October, and all 13 months disagree with the checkpoint. | IST calendar months. `domain.test.ts`, "our users are in India" (18:29:59 versus 18:30:00 UTC on the last day of a month). |
| 10 | Let through, fix before release | several | Not blockers for this PR, but needed before release: the list key is the index (screen :36), so rows recycle wrongly when the list changes (use the id); the address is hard-coded to the emulator (hook :6); no timeout, retry or `Retry-After` handling; `groupByMonth` and `monthTotal` run on every render over 4,600 rows (screen :24-29); nothing is stored, so offline shows an empty screen; the cursor is put into the URL without encoding (hook :29); no accessibility labels; no tests. | Id keys, a server address setting, a 15 s timeout with 4 attempts and `Retry-After`, memoised list building, SQLite storage, 104 unit and sync tests. |

I would also ask for the tests in comments 1, 3, 4 and 8 before the PR is merged. Each one is a few lines with a fake `fetch`, and none of them exists yet.
